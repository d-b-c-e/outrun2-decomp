# Sun preparation and per-view render state

The default runtime retains the original one-view sun. Step1 separated shared preparation from per-view render state. Step2 now routes the sun through three independent source cameras only under the existing admitted `OR2_CURVE_COMPOSITOR=1` Angled developer profile. Original, nondeveloper, offscreen and refused-source paths retain the legacy wrapper. No new setting or developer flag was added; rendered qualification remains open.

`native_sun_prepare_frame` resolves the stage, lens-flare offsets and shared light direction/world point, captures size/intensity/pause/native camera inputs, and advances the authored+12 countdown once when unpaused. The caller prepares once for a frame. `native_sun_render_view` consumes that immutable frame, explicit view data, one NativeSunViewState and a caller-owned two-byte flicker span. It does not rerun stage/direction/blended-eye/countdown preparation.

Each view state owns visibility calibration, first-result state, previous samples, pending record/matrix, saved occlusion render states and its logical query handle. The device owns the underlying query resource, as in the legacy path. Flicker storage is explicit: the legacy wrapper aliases the original+10 work word, preserving its update timing; the developer panel contexts supply separate storage. The default wrapper remains one preparation plus one render. Existing center visibility, edge fade, native lighting/queue/state/math and fallback behavior remain.

A preparation is not deduplicated automatically by frame number: its caller owns the once-per-frame contract. Both routes prepare once per invocation. The public functions are game-internal source seams, not a new C ABI or user setting. Explicit source inputs also carry off-axis screen offsets; the legacy branch leaves them disabled.

## Step2 developer routing checkpoint

The desktop sun provider reuses `triple_views` (the curved-source views of the old curve prototype were removed on 2026-11-13: curved screens now draw the flat views and bend them afterwards). These are the exact rotations/projections whose product forms the world GS correction. CPU sun view = native view * source rotation. Its inverse supplies eye/target and the flare screen matrix; source projection supplies focal scales and off-axis offsets for the sun gate/fade.

`SunView` remains a world-source phase for the compositor, but never admits GS replication. D3D11 binds only the named panel viewport/scissor; the CPU and native GPU vertex paths apply the matching widened-source pixel-centre scale. This avoids finishing/compositing the world before the flare. A renderer-owned scope sets/restores the native View/Projection, derived shader matrices and CPU culling view. Its culling frustum describes only that source eye, not the three-eye union. Before switching views, unrelated queued work is drained; every view also drains its final queued glow before camera/phase restoration.

Each panel retains independent query/calibration/previous-result/flicker state. An external native flicker-word change seeds all contexts; each advances separately, and the centre context writes back the native word. Shared preparation/countdown runs once. The global native visibility scratch is restored after the loop. Main culling/camera/projection state and caller phase/panel are restored, including camera-scope exceptions.

D3D11 previously inherited software occlusion queries; GPU draws bypass that software sample counter. The new SunView route creates independent native D3D11 queries, issues Begin/End around actual GPU draws, and uses nonblocking `GetData(...DONOTFLUSH)` with each context's previous samples while pending. Query resources are device-owned. Legacy query behavior is unchanged. These native GPU calls have been compiled, **not executed or qualified** in this checkpoint.

# `outrun-producer@2` software preview

This source-only candidate corrects the force model's input meanings. It is **not selected for OutRunDesktop wheel output**, is not in the F6 panel or `[FFB]` settings, and cannot send force to a device. An explicit ordinary-process switch can write a separate software-only trace from the just-completed car-control observer. The existing `outrun-legacy@1` code, trace and goldens remain unchanged. Those goldens reproduce the old Tweaks calculation with synthetic inputs; they do **not** establish tyre forces in this game's car record. The owner's installed tune is not migrated or reinterpreted.

## Pin and fixed preview profile

`windows/vendor/native/forcemodel/force_model.h` is byte-for-byte toolkit `native/forcemodel/force_model.h` at `fb710dffa29f707d296f1f579851e23d549a8b51`, SHA-256 `C7F3C3FF9C6D1475B88015643AFB1B515D3F6F97BCC46E1FE2082F26DED1B16F`. The adapter uses its `Model`, `Inputs` availability flags and `Shaper`. The provisional software profile fixes spring strength at `0.30`, full spring speed at `30 m/s`, and symmetric shift strength at `0.05`; damping, tyre load, texture, impact and weight transfer are off. Shaper gain is unity, with no extra fade, smoothing or ramp in this offline preview. None of these constants comes from or changes the owner's tune.

## Sample contract

The desktop `input_filter` runs at `xbox/source/main.cpp:246`, before the next native race update. Its car bytes are therefore the **previous completed car tick**. `race_input.cpp:73-96` computes signed steering in `analog_7d6810.current[0]` (-127..127); `race_player_car.cpp:375` passes that consumed value to `operation_input_49fad0`, and `pc_common_control.cpp:2189-98` writes it shifted left by 8 at car `+0x202` in GAME. Positive game steering produces a negative centering request through the toolkit model. The sign at a particular physical wheel is still unmeasured.

`pc_common_control.cpp:1039-46` produces `+0x1F8` for the HUD; `race_hud_navi.cpp:691-704` displays that metric base unchanged or multiplied by `0.6215` for miles. The request uses `speed_mps = hud_kmh_1f8 / 3.6`. `pc_transmission.cpp:6-35` updates gear `+0x208`. A change between two valid, nonzero gears in one continuous car generation emits one `gear_shift` event. It does not fire on the first sample, a menu return, a new race or a respawn.

The pure `Frame` requires an external, nonzero race epoch and car generation, a strictly consecutive source tick **within one epoch and car generation**, positive bounded `dt`, and proof that `OperationInput` ran for this car on that source tick. The source counter may restart when identity changes. The bytes alone cannot establish that proof. The game's `+0xD50 > 120` branch skips the `+0x202` write, so the adapter independently rejects that stale-steering case. A menu/pause/goal frame, invalid input, source-tick gap, new epoch or changed car generation resets gear history, model state and shaped output. A newly entered epoch or generation primes with zero output. The optional desktop observer witnesses successful `0x4A6ED0` init, direct GamePlCar control and the exact `0x49FAD0` steering write. It does not prove that every in-race teleport/recovery reinitializes the car; physical integration remains gated on that question.

Only `Inputs.has_steer`, `steer`, `speed_mps` and one-tick `gear_shift` can be populated. `has_steer_rate`, `has_front_lateral_force`, `has_lateral_g`, `has_longitudinal_g`, `has_slip` and `has_drift` stay false. Texture and impact stay zero. Car `+0x1D0/+0x1D4` are speed differences, and `+0x264/+0x268` are road-edge cross-distances, so they never enter these request fields. `+0x24C..+0x258` surface words can be stale when road result 1 skips their write, so they remain unavailable too.

`trace_header()` and `trace_csv()` expose the versioned `dbce.outrun-producer-ffb-trace@2` software row, including the consumed `dt_seconds` so event evolution can be replayed. This is a separate trace schema; it neither rewrites the legacy trace nor writes a runtime file. The fixture `test_ffb_producer2` exercises the actual `pc_input_analog_453860`, `operation_input_49fad0` and `manual_transmission` producers, previous-tick sampling, sign, shift count, unavailable fields and neutral/reset gates. Its synthetic car record verifies source behavior; it is not a rendered/gameplay or physical wheel qualification.

## Optional just-completed runtime shadow

Set `OR2_FFB_PRODUCER2_SHADOW_TRACE` to an absolute path before starting an **ordinary, non-recording** desktop process. The file is created only if absent. Without the switch there is no observer registration, model instance or file. Record requests refuse the switch; latched tests and Playback clear it before configuration. The F6 panel remains outermost in the input chain; it does not start recording. This path may coexist with the legacy `OR2_FFB_TRACE` software trace, but the legacy schema and wheel delivery are unchanged.

The native observer runs after direct GamePlCar control and reads signed consumed steer `+0x202`, HUD speed `+0x1F8` and gear `+0x208` from that just-completed control body. It requires a successful car init, mode 16, a witnessed same-call `0x49FAD0` write, signed `+0xD50 <= 120`, no game fault, and no PasPlCar nesting. Its source tick is a per-generation control-attempt ordinal, including rejected attempts. F6 open and `event_state.pause_depth > 0` reset the shadow even when mode stays 16 or no car callback runs. A new race epoch or car generation primes silently. A repeated `(frame_counter_95af0c, update_index_8a8cdc)` native tick pair resets/refuses the duplicate.

Shadow CSV rows add the native tick pair and gate reason before the pure @2 columns. The shadow's header says `seam=just-completed-car-control`; the pure adapter's `previous-completed-car-tick` header describes its original input-filter fixture and is not used here. An @1 legacy row samples **before** an update, whereas an @2 shadow row samples **after** completion. Frame numbers alone therefore do not align their measurements exactly. The shadow cannot send a wheel command. Observer exceptions and file write failures detach/reset only this optional trace, leaving game success, input, and legacy FFB unaffected. `test_ffb_shadow` exercises the gates and injected failures with a fake writer; no game, device, or physical force is involved.

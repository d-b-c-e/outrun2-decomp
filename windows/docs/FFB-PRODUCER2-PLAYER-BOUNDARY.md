Source audit at `1c2df54f4abc0c929f590c32927ffa9d8595859c`, following the one-run [ordinary software witness](https://github.com/d-b-c-e/dbce-project-mgmt/blob/main/artifacts/outrun-ffb-shadow-20261013/run-01/README.md). This document also records the bounded scripted recovery witness and the selected-model source adapter. Neither witness qualifies physical force output.

## Car continuity that exists now

`native_car_select.cpp` increments `race_inits` after successful `GamePlCar_Init` (`0x4A6ED0`) and clears `producer_active` on `GamePlCar` destruction (`0x49F4E0`). `race_player_car_control_4a8330` increments `producer_attempt` on every direct or nested call, then notifies the observer after the control body returns. The freshness gate requires a direct dispatch, active successful init, successful control, witnessed same-call `OperationInput` steering write, and the car record's own stale-steer gate. The shadow also resets on mode exit, pause depth, F6 open, failed freshness, a duplicate native tick pair, source-tick gap or new `race_inits`. The ordinary witness had one physical init/generation throughout, with consecutive fresh ticks on each side of F6; it cannot validate a mid-race car discontinuity.

The following **in-place** recovery paths can alter that same car work without a new `0x4A6ED0`, so `race_inits` alone cannot invalidate @2 history:

The software-only shadow now carries an explicit `producer_continuity` token from successful player tow/snap calls through the observer. A delayed tow also sets `producer_recovery_pending`, holding output neutral until the countdown's immediate snap clears it. A successful traffic-crash tow that mutates shared player body/wheel work increments the same token without treating traffic-event staging as a player countdown. Each transition records zero, discards model/shaper and gear history, and the next proven direct control sample primes. The pure @2 CSV still uses `car_generation` for successful init count; the optional shadow schema is separately versioned `dbce.outrun-producer-ffb-shadow-trace@3` with `continuity_token` and `recovery_pending` columns. No position-jump heuristic is used. Source fixtures cover the public wrecker dispatch, delayed countdown/snap, duplicate/failed callbacks, pause and race exit.

The one-route natural road-edge attempt was inconclusive: its 2,061 @3 rows remained generation 1/token 0. The subsequent [scripted witness](https://github.com/d-b-c-e/dbce-project-mgmt/blob/main/artifacts/outrun-ffb-scripted-20261013/run-01/analysis.md) used a special OFF-by-default Windows desktop build and the exact `OR2_DEV_SCRIPTED_RECOVERY=delayed-once` child switch on a muted disposable copy. After 300 eligible direct controls, it invoked the production `pc_pl_wrecker` phase-2 callback once. The 1,317-row trace has generation 1/token 0 Computed at frame 2064, token 1 neutral `recovery-pending` at 2065, token 2 neutral `recovery-snap` at 2068, then Primed at 2069 and Computed at 2070. Frame 2069 primed while gear 2 was observed; frame 2070 observed real gear 1 and produced the model's 0.05 shift cue. That is a post-prime observed gear change, not a stale continuity carryover. The run exited normally and restored the copy and lease. It proves this scripted software path only; ordinary natural recovery, wheel polarity, physical output and release remain unqualified. This is a finite call-site audit, not a reason to invent tire signals.

## Settings and output boundary

The current path in `ffb_settings.cpp` parses the mod-derived `[FFB] FFBPreset` and `FFB*` keys into `LegacySettings`; `ffb_live.cpp` creates `LegacyForce` at the pre-update input filter, then sends its integer intent through `ffbdev::Delivery` only if `[FFB] Output = wheel` and all existing gates permit it. `desktop_panel.cpp` uses those same legacy keys for its FFB page. `Output` is a separate next-start choice, default `none`; `DBCE_FFB_MUTE`, process kind, wheel identity, front-window and Stop FFB/F8 gates remain authoritative.

@2's reference `preview_model_settings()` fixes spring strength `0.30`, full-spring speed `30 m/s`, shift strength `0.05`, and all unavailable damping, lateral, tyre, texture and impact terms off. `preview_shaper_settings()` uses strength `50` (unity), inversion off, zero extra fade/smoothing/ramp. The observer computes after direct car control, a different seam from the legacy pre-update filter. The owner's accepted legacy preset is not a valid automatic @2 tune.

The selected path parses an explicit `[FFB] Model` identifier: absent or `outrun-legacy@1` retains the existing legacy path; `outrun-producer@2` selects the producer request path; empty or unknown identifiers refuse before the WheelFfb DLL loads. `[FFBProducer2] SteeringStrengthPercent` and `ShiftStrengthPercent` are strict independent integers from 0 to 100, each defaulting to the STD-027 reference 50. Malformed values refuse the selection. The steering control scales only the current arcade speed-and-steer centering estimate (provisional spring coefficient 0.30, full spring at 30 m/s); the shift control scales only the supported gear cue (reference 0.05). Both scale before composition; the shaper stays at unity strength 50. No legacy value is migrated or relabeled, and unsupported cornering load, grip loss, road texture, wall impact and damping remain unavailable. This estimate is not measured tire force; inversion and physical wheel polarity remain unqualified.

`SelectedRequests` remains a pure fixture seam. Runtime @2 now uses the same @3 gate and @2 stream through one car observer; the selected request sink remains active when optional CSV tracing is absent or fails. The trace header names the selected model and both effective gain percentages. A finite shaped request is clamped to `[-1,1]` and converted once to `[-10000,10000]` DirectInput units, without the legacy global gain. `ffbdev::Delivery` retains device identity, ownership, mute, front-window, F6, F8, watchdog and shutdown gates. A request observed just after completed car control is consumed at the **next input filter tick**. The software model advances when GAME is active, unpaused, the F6 panel is closed, and the producer sample is fresh, even if physical output is disabled or the window is not foreground. Missing callbacks, pause, F6 and recovery still reset it. Physical delivery receives zero behind its existing front/device gates; when an actual delivery gate reopens, the cached request is discarded and the first new direct callback primes before torque can resume. Bounded runtime transition notes label the selected model gate separately from disabled, not-front, or passing-to-Delivery output state, including requested output and any load refusal. The selected-request CSV records producer rows, including producer-neutral rows, but excludes delivery-only and gate zeros. It is **not a delivered-force trace** and cannot prove what the wheel held. F6 shows shared current/next-start output state and Stop FFB save errors for every model while hiding the legacy sliders for producer@2 and refused selections. There is no @2 F6 editor yet. Fake-native wiring tests cover request delivery, missed callback, recovery, panel, focus, menu, pause, invalid input, stop and shutdown; the correction has no new game-runtime or physical-output qualification.

The first muted selected-model [ordinary run](https://github.com/d-b-c-e/dbce-project-mgmt/blob/main/artifacts/outrun-ffb-selected-20261013/run-01/analysis.md) at source `3ad9296` exited normally and restored the disposable copy, but all 1,369 fresh request rows were Primed, with no Computed force. The tape did not record foreground state, so front-window ineligibility is an inference from the old coupled filter, not an observed fact. It is not a passing force-computation witness, and the same route was not repeated unchanged. The software/delivery split above is subsequent source work and requires focused review before any further rig witness.

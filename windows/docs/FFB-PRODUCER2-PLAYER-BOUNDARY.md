# Boundary from producer@2 shadow to a selectable player model

Source audit at `1c2df54f4abc0c929f590c32927ffa9d8595859c`, following the one-run [ordinary software witness](https://github.com/d-b-c-e/dbce-project-mgmt/blob/main/artifacts/outrun-ffb-shadow-20261013/run-01/README.md). The ordinary witness saw direct control, movement, signed steering and an F6 panel neutral/re-prime; it did not exercise a crash, tow, teleport, car replacement or physical wheel. This document also records the bounded scripted recovery witness and the selected-model source adapter. Neither witness qualifies physical force output.

## Car continuity that exists now

`native_car_select.cpp` increments `race_inits` after successful `GamePlCar_Init` (`0x4A6ED0`) and clears `producer_active` on `GamePlCar` destruction (`0x49F4E0`). `race_player_car_control_4a8330` increments `producer_attempt` on every direct or nested call, then notifies the observer after the control body returns. The freshness gate requires a direct dispatch, active successful init, successful control, witnessed same-call `OperationInput` steering write, and the car record's own stale-steer gate. The shadow also resets on mode exit, pause depth, F6 open, failed freshness, a duplicate native tick pair, source-tick gap or new `race_inits`. The ordinary witness had one physical init/generation throughout, with consecutive fresh ticks on each side of F6; it cannot validate a mid-race car discontinuity.

The following **in-place** recovery paths can alter that same car work without a new `0x4A6ED0`, so `race_inits` alone cannot invalidate @2 history:

The software-only shadow now carries an explicit `producer_continuity` token from successful player tow/snap calls through the observer. A delayed tow also sets `producer_recovery_pending`, holding output neutral until the countdown's immediate snap clears it. A successful traffic-crash tow that mutates shared player body/wheel work increments the same token without treating traffic-event staging as a player countdown. Each transition records zero, discards model/shaper and gear history, and the next proven direct control sample primes. The pure @2 CSV still uses `car_generation` for successful init count; the optional shadow schema is separately versioned `dbce.outrun-producer-ffb-shadow-trace@3` with `continuity_token` and `recovery_pending` columns. No position-jump heuristic is used. Source fixtures cover the public wrecker dispatch, delayed countdown/snap, duplicate/failed callbacks, pause and race exit.

The one-route natural road-edge attempt was inconclusive: its 2,061 @3 rows remained generation 1/token 0. The subsequent [scripted witness](https://github.com/d-b-c-e/dbce-project-mgmt/blob/main/artifacts/outrun-ffb-scripted-20261013/run-01/analysis.md) used a special OFF-by-default Windows desktop build and the exact `OR2_DEV_SCRIPTED_RECOVERY=delayed-once` child switch on a muted disposable copy. After 300 eligible direct controls, it invoked the production `pc_pl_wrecker` phase-2 callback once. The 1,317-row trace has generation 1/token 0 Computed at frame 2064, token 1 neutral `recovery-pending` at 2065, token 2 neutral `recovery-snap` at 2068, then Primed at 2069 and Computed at 2070. Frame 2069 primed while gear 2 was observed; frame 2070 observed real gear 1 and produced the model's 0.05 shift cue. That is a post-prime observed gear change, not a stale continuity carryover. The run exited normally and restored the copy and lease. It proves this scripted software path only; ordinary natural recovery, wheel polarity, physical output and release remain unqualified. This is a finite call-site audit, not a reason to invent tire signals.

## Settings and output boundary

`ffb_settings.cpp` retains the mod-derived `[FFB] FFBPreset` and `FFB*` keys as `LegacySettings`. The legacy raw adapter still names `+0x1D0/+0x1D4` as steering/rate although their producers write speed differences; `+0x264/+0x268` are road-edge cross-distances, not tire loads. Rather than silently changing the old tune's meaning, `ffb_live.cpp` limits `LegacyForce` to `OR2_FFB_TRACE` or latched software traces. Absent or explicit Legacy with saved `Output = wheel` refuses before `WheelFfb_Load` / `Delivery::start`, naming producer@2 as the wheel-capable model. The legacy calculation, raw adapter, old keys, goldens and trace schemas remain unchanged.

F6 exposes the two existing model IDs through **Force model at the next start**, saving only `[FFB] Model`. Legacy is clearly labeled software trace-only, including when Output is saved On. The separate output switch saves only `Output = wheel | none`, default `none`; turning it On never selects a model. Controls follow the next-start model and keep both gain sets independent. Unsupported saved model identifiers remain untouched until an explicit valid choice. Model and strength edits never change this session's model or applied gains. `DBCE_FFB_MUTE`, process kind, wheel identity, front-window and Stop FFB/F8 gates remain authoritative for producer@2 delivery.

@2's reference `preview_model_settings()` fixes spring strength `0.30`, full-spring speed `30 m/s`, shift strength `0.05`, and all unavailable damping, lateral, tyre, texture and impact terms off. `preview_shaper_settings()` uses strength `50` (unity), inversion off, zero extra fade/smoothing/ramp. The observer computes after direct car control, a different seam from the legacy pre-update filter. The owner's accepted legacy preset is not a valid automatic @2 tune.

The selected path parses an explicit `[FFB] Model` identifier: absent or `outrun-legacy@1` selects only the historical software reference; `outrun-producer@2` selects the producer request path; empty or unknown identifiers refuse before the WheelFfb DLL loads. `[FFBProducer2] SteeringStrengthPercent` and `ShiftStrengthPercent` are strict independent integers from 0 to 100, each defaulting to the STD-027 reference 50. Malformed values refuse the selection. The steering control scales only the current arcade speed-and-steer centering estimate (provisional spring coefficient 0.30, full spring at 30 m/s); the shift control scales only the supported gear cue (reference 0.05). Both scale before composition; the shaper stays at unity strength 50. No legacy value is migrated or relabeled, and unsupported cornering load, grip loss, road texture, wall impact and damping remain unavailable. This estimate is not measured tire force; inversion and physical wheel polarity remain unqualified.

`SelectedRequests` remains a pure fixture seam. Runtime @2 now uses the same @3 gate and @2 stream through one car observer; the selected request sink remains active when optional CSV tracing is absent or fails. The trace header names the selected model and both effective gain percentages. A finite shaped request is clamped to `[-1,1]` and converted once to `[-10000,10000]` DirectInput units, without the legacy global gain. `ffbdev::Delivery` retains device identity, ownership, mute, front-window, F6, F8, watchdog and shutdown gates. A request observed just after completed car control is consumed at the **next input filter tick**. The software model advances when GAME is active, unpaused, the F6 panel is closed, and the producer sample is fresh, even if physical output is disabled or the window is not foreground. Missing callbacks, pause, F6 and recovery still reset it. Physical delivery receives zero behind its existing front/device gates; when an actual delivery gate reopens, the cached request is discarded and the first new direct callback primes before torque can resume. Bounded runtime transition notes label the selected model gate separately from disabled, not-front, or passing-to-Delivery output state, including requested output and any load refusal. The selected-request CSV records producer rows, including producer-neutral rows, but excludes delivery-only and gate zeros. It is **not a delivered-force trace** and cannot prove what the wheel held. F6 shows current and next-start model/output state and Stop FFB save errors. Selecting producer@2 for the next start exposes its independent steering/shift controls and saves their integer `[FFBProducer2]` values; selecting Legacy exposes only its software trace controls. The current session status continues to show the unchanged model and applied gains. Invalid saved producer values are flagged and preserved until their own controls are edited. Fake-native wiring tests cover request delivery, missed callback, recovery, panel, focus, menu, pause, invalid input, stop and shutdown; the gain editor has no new game-runtime or physical-output qualification.

The first muted selected-model [ordinary run](https://github.com/d-b-c-e/dbce-project-mgmt/blob/main/artifacts/outrun-ffb-selected-20261013/run-01/analysis.md) at source `3ad9296` exited normally and restored the disposable copy, but all 1,369 fresh request rows were Primed, with no Computed force. The tape did not record foreground state, so front-window ineligibility is an inference from the old coupled filter, not an observed fact. The same route was not repeated unchanged. After focused review of the software/delivery split, the changed-candidate run 02 at source `0979631` produced 1,368 Computed fresh rows with finite positive and negative requests. Its Help boundary was zero and computation resumed after close; the ordinary route supplied no steering after Help, so post-panel nonzero onset was not witnessed. The hub retains the run under `artifacts/outrun-ffb-selected-20261013/run-02`. Neither run establishes delivered wheel torque.

Physical force remains unqualified: ordinary recovery, output gating, wheel polarity, onset and stop behavior still need owner-attended acceptance. The software already has an explicit gated producer@2 delivery path; this is not a claim that physical activation is technically impossible. No owner configuration, installed executable or Output setting is changed by this source patch. A native deployment must pair the built semantics with the hash-bound optional capability block `ffb: {models: ["outrun-legacy@1", "outrun-producer@2"], wheelOutput: ["outrun-producer@2"], legacy: "trace-only"}`. A newer external generator alone is not evidence for that declaration; pre-change installations without the block retain their historical behavior.

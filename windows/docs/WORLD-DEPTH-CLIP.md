# Defer world depth clipping until panel correction

The type2 XYZ particle increment removed the emitter's center-W rejection, but that was only the first consumer. D3D11 `draw_primitive_up` calls the shared software state's real XYZ decoder and `triangle`, which clipped against center `z >= 0`, `z <= w` and positiveW before the virtual `raster` hook. The three-view geometry shader runs later. A triangle already removed or cut to the center near plane could not be recovered for a side panel. Frozen8b451ab and earlier candidates retain this source integration gap; their packet fixtures did not establish complete admission.

The shared software device now has a protected GPU-depth-clipping capability, false by default. D3D11 requests it only with Angled's callback installed, World phase and logical backbuffer. The actual triangle consumer forwards the three original finite homogeneous positions and attributes to the backend; it does not divide by centerW or clip to the center near/far planes. D3D11 applies panel corrections before its hardware depth clip. If a projection is refused or a program is unmatched, the existing single-view GPU fallback still owns clipping. No simulation/display frame is repeated.

Software devices, ordinary Off/Planar, HUD/frontend/unclassified phases and reflection/offscreen targets keep the existing CPU clipper. Nonfinite homogeneous geometry is refused before backend submission. RHW darkening keeps its separate explicit WorldCoverage route. Defaults, camera state, event data, targets, stencil/blend settings and owner files are unchanged.

`test_world_depth_clip` drives actual XYZ DrawPrimitiveUP decode -> triangle -> virtual raster using a CPU recording backend and the exact admission predicate used by D3D11. The baseline fails on a triangle behind the center but wholly inside the real right-panel frustum. With deferral it passes **57 assertions**: unchanged front clip positions/colour/UV, original negative-W triangle reaches the backend, a near-plane-crossing triangle retains three original vertices rather than the CPU-clipped four, and ordinary/software/HUD/frontend/offscreen/no-Angled/nonfinite controls. This is a backend boundary assertion; no D3D11 device, shader execution or rendered pixels are tested.

Active point-sprite route6 remains a distinct earlier rejection: event sources8/9/10 use `41AE40`, then `PcSoftD3D9Device::draw_primitive_up` calls `pc_point_sprite_corners` before `triangle`. That helper rejects center W/depth and fully outside-center squares. This increment cannot recover those points. Route5 `41A6F0` shares that backend behavior. Legacy types0/1 RHW and type4 lines exist in the dispatcher but are assigned by no current PART_EFC initializer; prioritize the active route6 and other projected-effect consumers before expanding dormant paths. These are source findings, not observed in-game failures. Type3 tire smoke/water/misc/backfire already uses world XYZ billboard geometry and shares the newly qualified triangle handoff.

Required GPU qualification remains: exact candidate counter/images, side admission and occlusion through motion/pause/replay, full shadow stencil/darkening alignment, subsequent XYZ constants, UI and reflections, MSAA/depth behavior, cost and owner acceptance. Curve UV/source matrices remain unconnected to a compositor. This source change does not enable curved presentation or always-corrected defaults.
